\plt{This template document assumes that a single program is being documented.
  If you are documenting a family of models, you should start with a commonality
  analysis.}

\plt{The SRS is not generally written, or read, sequentially.  The SRS is a
  reference document.  It is generally read in an ad hoc order, as the need
  arises.}

\plt{Guiding principles for the SRS document:
\begin{itemize}
\item Do not repeat the same information at the same abstraction level.  If
  information is repeated, the repetition should be at a different abstraction
  level.
\end{itemize}
}

\plt{The template description comments should be disabled before submitting this
  document for grading.}

\plt{You can borrow any wording from the text given in the template.  It is part
  of the template, and not considered an instance of academic integrity.  Of
  course, you need to cite the source of the template.}

\plt{When the documentation is done, it should be possible to trace back to the
  source of every piece of information.  Some information will come from
  external sources, like terminology.}

\plt{An SRS document should have the following qualities: unambiguous,
  consistent, complete, validatable, abstract and traceable.}

\plt{The overall goal of the SRS is that someone can learn,
  understand and verify the captured domain knowledge.  They should not have to
  trust the authors of the SRS on any statements.  They should be able to
  independently verify/derive every statement made.}

\subsection{Characteristics of Intended Reader} \label{sec_IntendedReader}

\plt{This section summarizes the skills and knowledge of the readers of the
  SRS.  It does NOT have the same purpose as the ``User Characteristics''
  section (Section~\ref{SecUserCharacteristics}).  The intended readers are the
  people that will read, review and maintain the SRS.  They are the people that
  will conceivably design the software that is intended to meet the
  requirements.  The user, on the other hand, is the person that uses the
  software that is built.  They may never read this SRS document.  Of course,
  the same person could be a ``user'' and an ``intended reader.''}

\plt{The intended reader characteristics should be written as unambiguously and
  as specifically as possible.  Rather than say, the user should have an
  understanding of physics, say what kind of physics and at what level.  For
  instance, is high school physics adequate, or should the reader have had a
  graduate course on advanced quantum mechanics?}

\subsection{User Characteristics} \label{SecUserCharacteristics}

\plt{This section summarizes the knowledge/skills expected of the user.

  requires knowledge of a typical user.  As mentioned above, the user is a
  different role from the ``intended reader,'' as given in
  Section~\ref{sec_IntendedReader}.  As in Section~\ref{sec_IntendedReader}, the
  user characteristics should be specific an unambiguous.  For instance, ``The
  end user of \progname{} should have an understanding of undergraduate Level 1
  Calculus and Physics.''}

\subsection{System Constraints}

\plt{System constraints differ from other type of requirements because they
  limit the developers' options in the system design and they identify how the
  eventual system must fit into the world. This is the only place in the SRS
  where design decisions can be specified.  That is, the quality requirement for
  abstraction is relaxed here.  However, system constraints should only be
  included if they are truly required.}

\plt{This is where you would mention platform constrains, and licensing
restrictions.}

\textbf{Primary Actor}

User

\textbf{Preconditions}

\refstepcounter{ucnum}\label{UC_EarnCurrency}
\subsection{\ucref{UC_EarnCurrency}: Earn Virtual Currency}

\textbf{Primary Actor}

User

\textbf{Preconditions}
\begin{itemize}
\item The user has recorded a supported activity.
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
\item The system retrieves the user's recorded activity.
\item The system calculates the virtual currency earned.
\item The system applies the daily earning limit.
\item The user's currency balance is updated.
\end{enumerate}

\textbf{Alternative Flows}
\begin{itemize}
\item If no eligible activity is recorded, no currency is awarded.
\item Activity exceeding the daily cap earns no additional currency.
\item If an activity record exceeds the plausibility limits for its type,
the system does not count it toward currency, trends, streaks or
milestones and informs the user (HA SEC-1).
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
\item The user's currency balance reflects the earned rewards.
\end{itemize}

\refstepcounter{ucnum}\label{UC_BuyAsset}
\subsection{\ucref{UC_BuyAsset}: Buy a Simulated Asset}

\textbf{Primary Actor}

User

\textbf{Preconditions}
\begin{itemize}
\item The user has enough virtual currency for the purchase.
\item A usable market price is available.
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
\item The user selects an asset to purchase.
\item The user enters the quantity.
\item The system displays the total cost.
\item The user confirms the transaction.
\item The system updates the balance and holdings.
\end{enumerate}

\textbf{Alternative Flows}
\begin{itemize}
\item If the user has insufficient currency, the purchase is rejected.
\item If the transaction fails, the balance and holdings remain unchanged.
\item If the market price is outdated, the system does not allow the trade and informs the user.
\item If the market is closed, the system queues the trade until the market reopens.
\item If the user submits the same trade twice, the system only processes it once.
\item If this is the user's first trade, they must acknowledge that the market is simulated and does not provide financial advice.
\item If the user chooses to sell instead, the system checks their shares and adds the virtual currency from the sale to their balance.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
\item The purchase is recorded and the portfolio is updated.
\end{itemize}

\subsection{Privacy and Data Retention}
\label{SecPrivacyRetention}

\progname{} Collects account information, daily total activity, virtual currency balances, portfolio holdings, and information that the user has shared with friends. Due to the sensitive nature of this information, users must have control over how their data is collected, stored and shared.

\begin{description}

\item[SEC-7 (Least privilege health acess)]
The system shall request read access only to the supported health data types and shall not request permission to write to the health platform.

\textit{Fit criterion:} All requested health permissions are read only and correspond to supported activity data.

\item[SEC-6 (Permission Purpose)]
Before requesting a permission the system shall explain which feature requires the requested data.

\textit{Fit Criterion:} Every permission request is followed by an explanation of its purpose.

\item[SEC-7 (Consent and Withdrawal)]
The system shall get the users consent before is accessses health or location data and shall stop reading that information when the user's consent is withdrawn.

\textit{Fit Criterion:} No data is accessed before consent or after consent is withdraen.

\item[SEC-8 (Data Minimization)]
The system shall send only daily activity totals to the server rather than individual health record.

\textit{Fit Criterion:} Server requests contain daily totals without individual health events.

\item[SEC-9 (Third Party Data)]
The system shall not send personal, health, or locationd data to third parties.

\textit{Fit Criterion:} Requests to the market data provider contains only asset identifiers.

\item[SEC-10 (Private Sharing)]
The sytem shall keep user stats private unless the user explicitly chooses to share them.

\textit{Fit Criterion:} Shared statistics are only visible to the friends selected by the user.

\item[SEC-11 (Location Privacy)]
The system shall not include location, route, or exact activity time information in shared posts.

\textit{Fit Criterion:} Shared posts contain no exact location, route, or activity timestamps.

\item[SEC-12 (Authenticated Access)]
The system shall require authentication before it allows
access to private user information

\textit{Fit Criterion:} Requests without valid authentication
or authorization are rejected.

\item[SEC-13 (Data Protection)]
The system shall encrypt user data during the transmission of the data
and when the data is stored on the server.

\textit{Fit Criterion:} Network and storage inspection will
reveal no readable sensitive data that can be intercepted or accessed.

\item[SEC-14 (Session Expiry)]
The system shall end inactive sessions after a
defined session timeout.

\textit{Fit Criterion:} Expired sessions can no longer
authorize requests.

\item[SEC-15 (Account Deletion).]
The system shall allow users to delete their accounts
and remove personal information in the system within a
defined deletion period.

\textit{Fit Criterion:} Deleted accounts aren't able to sign in,
and associated records must be removed within a specified period.

\end{description}

\section{Rationale}

This section explains the reasoning behind the major requirements
and decisions made for \progname{}.

\subsection{Simulated Investing}

\progname{} uses virtual currency instead of real money so users
can learn about investing without the financial risk associated with investing. This allows
beginners to experiment with different investment decisions
without losing any real savings. The restriction on real money
transactions also keeps the system focused on education rather
than financial services (\scref{SC_NoRealMoney},
\rref{FR_MktBuy}).

\subsection{Activity Based Rewards}

The system rewards users for everyday physical activity in order to
encourage consistent exercise habits. Rather than requiring the user to do
specific individual workouts, the app uses activity that is already recorded by
the user's phone health platform. A daily earning limit is
enforced in order to discourage excessive exercise for virtual
rewards (\scref{SC_HealthPlatform},
\rref{FR_ActEarn}, \rref{FR_ActDailyCap}).

\subsection{Goals and Streaks}

Users can set their own activity goals and track their streaks
to stay motivated. Goals are optional because not every user
wants to follow a specific activity target. Rest days are also
included so users do not feel pressured to exercise every day
to maintain their streak. Missing a goal does not reduce
the user's currency or holdings
(\rref{FR_ActGoal}, \rref{FR_ActGoalOptional},
\rref{FR_ActRestDay}, \rref{FR_ActNoPenalty}).

\subsection{Financial Education}

Educational explanations and knowledge checks are included
because simulated trading alone may not help beginners
understand their investment decisions. By providing explanations
alongside market activity, users can learn financial concepts
while practising them. Portfolio feedback also helps users
understand the effects of their trades
(\rref{FR_LearnInPlace},
\rref{FR_LearnTradeEffect},
\rref{FR_LearnKnowledgeCheck}).

\subsection{Real-World Market Data}

The simulated market uses real-world prices to give users
a more realistic investing experience. However, outdated
prices could create unrealistic trading results. The system
therefore prevents trades using stale prices while the market
is open and queues trades requested while the market is
closed (\scref{SC_MarketData},
\rref{FR_MktRealPrices},
\rref{FR_MktNoStaleTrade},
\rref{FR_MktQueueClosed}).

Trades must also be recorded correctly to make sure users
do not lose virtual currency or receive incorrect holdings.
The system prevents duplicate trades and ensures that both
the user's balance and holdings are updated together
(\rref{FR_MktAtomicTrade},
\rref{FR_MktNoDuplicate}).

\subsection{Privacy and Social Features}

The social features are intended to motivate users without
requiring them to share private information. Users choose
which friends can view their updates, and personal body
measurements are excluded from shared content. Users can
also remove friends or delete shared updates to maintain
control over their information
(\rref{FR_SocialChooseFriends},
\rref{FR_SocialNoBody},

\subsection{Security and Data Protection}

Since the system stores personal information, activity totals,
and simulated investment records, protecting this data is
important. Users must be signed in before accessing private
information, and their data must be protected during storage
and transmission. Sessions also expire to reduce the risk of
unauthorized access

easy to understand, while supporting different levels of
physical activity and mobile device accessibility settings.
