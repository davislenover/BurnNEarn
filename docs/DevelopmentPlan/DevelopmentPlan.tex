This section describes how the team will use Git and GitHub to collaborate on both source code and documentation, how work will be tracked through issues, and how Continuous Integration and Continuous Deployment (CI/CD) will keep the project stable. 
It is written to serve as a guide for current and future contributors. The repository is available at \href{https://github.com/davislenover/BurnNEarn}{BurnNEarn GitHub Repository}.

\subsection{Branches}

The repository will have exactly one permanent branch:

\begin{itemize}
  \item \texttt{main}: the protected, stable branch representing the latest reviewed state of the project. Direct pushes are not permitted. 
  All changes must arrive through a pull request that has been approved by at least one other team member and has passed all CI checks.
\end{itemize}

All other branches are short-lived and must follow the naming convention \texttt{<type>/<name>-<description>}, where \texttt{type} is one of the categories in Table~\ref{TblBranchTypes}, \texttt{name} is the author's first name in lowercase, and \texttt{description} is a brief summary of the work in two to four words, separated by hyphens.

Branches are not shared between members; each member creates their own branch for each unit of work. 
For documentation, each member creates one branch per deliverable covering the sections assigned to them. For code, each feature or fix gets its own branch. Once a branch's pull request is merged into \texttt{main}, the branch is deleted. Before opening a pull request, the author updates their branch with the latest changes from \texttt{main} and resolves any merge conflicts locally, so that conflicts are never resolved during review.

\subsection{Commits}

Commits should be small and focused on a single change, rather than combining unrelated edits. 
Commit messages should begin with a short summary in the imperative mood (e.g., ``Add step count permission request'') and reference the related issue number where applicable (e.g., \texttt{\#14}), which links the commit to that issue on GitHub. 
Issues are closed through the pull request rather than individual commits, as described in Section~\ref{SecPullRequests}.

\subsection{Pull Requests} \label{SecPullRequests}

When the work on a branch is complete, the author follows these steps:

\begin{enumerate}
  \item Open a pull request into \texttt{main} with a title summarizing the change and a description of what was changed and why. The description must link the related issue using a closing keyword (e.g., \texttt{Closes \#14}), which automatically closes the issue when the pull request is merged.
  \item Request at least one reviewer. The reviewer should be a member working in a related area, or the whole team if the change affects everyone, such as shared document sections or the overall architecture.
  \item Address the reviewer's comments, which are left directly on the relevant lines of code or documentation.
  \item Once the pull request has one approval and all CI checks pass, the author merges it using a \textit{merge commit}, which preserves every individual commit from the branch on \texttt{main}. This keeps a complete record of each member's contributions throughout the project. The author then deletes the branch.
\end{enumerate}

Reviewers are expected to respond to a review request within 48 hours, or within 24 hours during the final three days before a deadline. 
For documentation, reviewers also check the changes against the deliverable's checklist and rubric before approving.

\subsection{Tags}

Deliverables are marked directly from the \texttt{main} branch, so a Git tag will be created on \texttt{main} at each deliverable's deadline to record exactly what was marked. 
Document deadlines use the format \texttt{<document>-<revision>} (e.g., \texttt{dev-plan-rev0}, \texttt{srs-rev0}, \texttt{design-rev-1}), and demonstrations use the format \texttt{<demo>-demo} (e.g., \texttt{poc-demo}, \texttt{rev0-demo}, \texttt{final-demo}). 
The team member who merges the final pull request before a deadline is responsible for creating its tag. 
Tags allow the team to return to the exact state of the project at each deadline, and to compare revisions when addressing feedback.

\subsection{Issue Management}

GitHub Issues will serve as the team's ticketing system, so that all work is visible, assigned, and traceable.

\begin{itemize}
  \item \textbf{Issue size:} Each issue should represent work that can be completed in a single sitting of roughly two to three hours. Larger tasks are split into multiple issues. For documentation, every section of each document has its own issue, titled with its deliverable and section (e.g., \texttt{[Development Plan] 7 Workflow Plan}).
  \item \textbf{Ownership:} Every task issue is assigned to one owner, who is responsible for completing it and moving it through the project board described in Section~\ref{SecGitHubProjects}.
  \item \textbf{Milestones:} Each deliverable is a milestone whose due date matches the deadline in Table~\ref{TblSchedule}. Every issue related to a deliverable is added to its milestone, so the team can see how much work remains before each deadline.
  \item \textbf{Meetings and lectures:} An issue is created for every team meeting, supervisor meeting, and lecture, and is tracked in its own column on the project board. At least 24 hours before a meeting, the agenda and any questions are added to the issue. Afterwards, notes and action items are recorded, each action item becomes its own issue, and the meeting issue is closed. Lecture issues record the topic, date and time, and attendance.
\end{itemize}

\subsection{Continuous Integration and Continuous Deployment}

GitHub Actions will run automated checks on the repository, so that errors are caught when a change is proposed rather than after it reaches \texttt{main}:

\begin{itemize}
  \item \textbf{Documentation:} On every pull request that changes the \texttt{docs} folder, all \LaTeX{} documents are compiled. 
  The check fails if any document does not build, and the generated PDFs are saved as downloadable artifacts of the workflow run, linked from the pull request, so reviewers can read the rendered changes.
  \item \textbf{Code:} Once development begins, every pull request and every push to \texttt{main} runs a linter and the automated test suite in the \texttt{test} folder. 
  Branch protection prevents a pull request from being merged if any check fails.
  \item \textbf{Deployment:} Once the core features are stable, targeted for Revision~0, every merge into \texttt{main} will automatically produce an internal test build of the mobile app, so the team and supervisor can always install the latest version on their phones.
\end{itemize}

If a check fails, the pull request's author is responsible for fixing it before requesting another review.

\section{Proof of Concept Demonstration Plan}

% What is the main risk, or risks, for the success of your project?  What will you
% demonstrate during your proof of concept demonstration to convince yourself that
% you will be able to overcome this risk?

This section identifies the main risks to the success of FitFolio, 
describes what the proof of concept (PoC) demonstration will show to convince the team that these risks can be overcome, 
and outlines what the team will do if the demonstration shows that a risk cannot be overcome as planned.

\subsection{Main Risks}

FitFolio depends on two external systems that no team member has worked with before. 
Both are implementation risks: if either cannot be made to work, the app's core loop of earning currency through activity and investing it in real assets cannot be built.

\begin{enumerate}
  \item \textbf{Reading fitness data from the phone's health platform.} FitFolio's core promise is that activity is tracked automatically. 
  This requires reading step data through Google Health Connect on Android and Apple HealthKit on iOS, which each have their own Application Programming Interfaces (APIs), permission models, and restrictions on when data can be read. 
  Since FitFolio will be built with React Native, it cannot access these platforms directly, and will depend on third-party libraries to bridge between the app and each platform. 
  These libraries may be incomplete, poorly maintained, or out of date with the latest platform versions, which the team does not control. If step data cannot be read reliably, the app cannot award currency fairly.
  \item \textbf{Valuing portfolios with real market prices.} The virtual portfolio must follow real asset prices, but market data providers limit how many requests can be made, especially on free plans. 
  If prices cannot be retrieved often enough within these limits, portfolio values will not follow the market closely enough to teach users how investing works.
\end{enumerate}

\subsection{Demonstration}

The PoC will show one minimal path through FitFolio's core loop, running on a physical Android phone:

\begin{enumerate}
  \item \textbf{Read the day's step count} (Risk 1). After the user grants permission, the app reads the current day's steps from Google Health Connect and displays them. This succeeds if the count matches the phone's own health app, and updates after the team member walks and reopens the app.
  \item \textbf{Convert steps into virtual currency} (connects Risks 1 and 2). The step count is converted into currency using a simple fixed rule, and the balance is displayed.
  \item \textbf{Buy a real asset with virtual currency} (Risk 2). The user spends their balance on shares of one real asset, such as a stock or Exchange-Traded Fund (ETF), at its current market price.
  \item \textbf{Show the portfolio's value following the market} (Risk 2). The portfolio's value is recalculated each time a new price is retrieved. This succeeds if the displayed value matches the asset's public market price at each update, and the number of requests used shows that the chosen update interval fits within the provider's free limits.
\end{enumerate}

If time allows, the same steps will also be shown on an iPhone using Apple HealthKit. This is a stretch goal rather than a requirement, so that the core demonstration stays achievable.

The PoC is deliberately not a prototype. It will have a minimal user interface and will not include user accounts, workouts, the social feed, or market scenarios. 
Its only purpose is to show that the two main risks can be overcome. The team will rehearse the full demonstration by the team deadline in Table~\ref{TblSchedule}, and the demonstrated version will be tagged \texttt{poc-demo} on \texttt{main}.

\subsection{If the PoC Fails}

If the demonstration shows that a risk cannot be overcome as planned, the team will adjust the project's scope rather than its core idea:

\begin{itemize}
  \item \textbf{If step data cannot be read reliably:} The team would first limit syncing to when the user opens the app, rather than in the background, which avoids most platform restrictions. If a third-party library proves unreliable, the team would switch to an alternative library, or write a small amount of platform-specific code to access the health platform directly.
  If one platform still cannot be supported, FitFolio would support only the platform that works, and the team would discuss with the supervisor whether the second platform should become a future goal. 
  If neither platform works, users would enter their activity manually as a last resort. Since this weakens FitFolio's promise of automatic tracking, the team would discuss this change in scope with the supervisor before adopting it.
  \item \textbf{If market data limits are too restrictive:} The team would reduce how often prices are updated (e.g., every 15 minutes, or once per day), have a server retrieve each price once and share it across all users rather than requesting it per user, and limit the app to a curated list of assets. 
  If a provider's limits or cost are still unworkable, the team would switch to a different provider.
\end{itemize}

\subsection{Secondary Risk}

A secondary risk is that the market scenarios, such as replays of past downturns, depend on historical price data that may be limited or costly to access. 
Since this feature is not part of the core loop, it will not be included in the PoC. If historical data proves difficult to obtain, the team would reduce the number of scenarios offered, or build them from a small set of stored historical datasets.

\section{Expected Technology}
The following section details the expected technologies for the systems the team will be developing. \newline
\subsubsection{Operating Systems}
The primary target operating systems for this app will be Android 17+ and iOS 27+. This is due to the nature of the testing equipment available
for all group members and the supervisor.

\subsubsection{Languages}
It is expected that React Native (TypeScript) will be used for the front-end. This will allow the team to write code that works on both platforms at once.
The backend will consist of Python mainly for its rich and optimal library support for the tasks the app may need to perform (e.g., fetching stock data over the web). Moreover, Python's NumPy and
pandas will be useful for modeling data within the market simulation engine.

\textit{Alternatives considered:} Flutter was considered for the front-end, but it uses Dart, a language less familiar to the team than TypeScript.
TypeScript (Node.js) was considered for the backend so the whole codebase would share one language, but Python's numerical libraries (NumPy and pandas) are better suited to the market simulation engine.

\subsubsection{Backend Framework}
The app will communicate with the Python backend through a REST API over HTTPS, exchanging data as JSON. The backend will be built with FastAPI, which validates requests using Python type hints
and automatically generates API documentation, helping keep the front-end and backend in agreement on what data is sent. Its support for asynchronous requests also suits fetching market data from external APIs.

\textit{Alternative considered:} Django (with Django REST Framework) was considered, but it includes many features the project does not need (e.g., server-rendered pages), which adds setup and boilerplate.

\subsubsection{Market Data}
Real-world stock market data will be retrieved from the Finnhub API, whose free tier provides current stock prices and company information. To stay within its request limits, fetched data will be
cached in the database (see Databases).

\textit{Alternative considered:} yfinance, an unofficial library that reads Yahoo Finance data, was considered as it is free and simple to use. However, it is not an official API and can stop working
without notice whenever Yahoo changes its website.

\subsubsection{Libraries}
The following libraries are expected to be used for React Native:
\begin{itemize}
    \item \href{https://github.com/kingstinct/react-native-healthkit}{@kingstinct/react-native-healthkit} - Provides access to HealthKit on iOS.
    \item \href{https://github.com/matinzd/react-native-health-connect}{react-native-health-connect} - Provides access to Health Connect on Android.
\end{itemize}
The following libraries are expected to be used for Python:
\begin{itemize}
    \item \href{https://numpy.org}{NumPy} - Handles numerical computing quickly (e.g., vector operations).
    \item \href{https://pandas.pydata.org}{pandas} - Data manipulation and analytics.
\end{itemize}

\textit{Alternative considered:} Writing custom native modules (in Swift and Kotlin) to access HealthKit and Health Connect directly was considered, but existing bridge libraries avoid the need to
write and maintain code in two additional languages.

\subsubsection{Databases}
User data, portfolios, the social feed and cached market data (as pulling constantly from an API will likely be expensive) will be stored in PostgreSQL.

\textit{Alternative considered:} MongoDB was considered for its flexible document storage. However, the app's data is highly relational (e.g., users, their portfolios, trades and friends), and trades must be
recorded reliably, which PostgreSQL's relations and transactions handle well.

\subsubsection{Testing}
For unit testing, Jest will be used for the front-end as this works directly for React. For the backend, pytest will be used as this works well with Python and doesn't require a lot of boilerplate class code
(unlike Python's built-in unittest), therefore allowing the team to test much quicker.

\subsubsection{Linting and Formatting}
ESLint and Prettier will be used for the front-end: ESLint catches common mistakes in TypeScript code, and Prettier formats code automatically. For the backend, Ruff will be used as a single tool that
both lints and formats Python code. These checks will run in CI on every pull request and must pass before it can be merged (see Definition of Done).

\textit{Alternative considered:} For Python, Black (formatting) with Flake8 (linting) was considered, but Ruff covers both in one tool and runs considerably faster.

\subsubsection{Continuous Integration}
The following subsection outlines how CI/CD will be utilized within this project: \newline
CI will happen within a pull request, using GitHub Actions, before code is merged on the main branch, there will be a standard set of tests which will be run to ensure no regression occurs.
For the tests themselves, they will be developed over time and integrated into the suite as new features are developed. New test cases are required for a feature to be merged to main unless otherwise

For anything backend related, a PostgreSQL container will be run such that any feature/system that utilizes queries can be tested.

\section{Coding Standard}

The development team will adopt a standard based on the Microsoft TypeScript Coding Guidelines
as the primary guideline for TypeScript code written throughout the project.
\href{https://github.com/microsoft/TypeScript/wiki/Coding-guidelines}
{Microsoft TypeScript Coding Guidelines}

The team will follow applicable conventions from this guideline, including:


\begin{itemize}
    \item Using PascalCase for type names and enum values
    \item Using camelCase for functions, properties, and local variables
    \item Avoiding the use of the I prefix for interface names
    \item Separating logical components into appropriate files
    \item Exporting types and functions only when they are required by other modules
    \item Placing type definitions before their use where practical
    \item Preferring undefined over null
    \item Using double quotation marks for strings.
    \item Using four spaces for indentation
\end{itemize}

Some standards in the Microsoft TypeScript Coding Guidelines do not 
apply directly to FitFolio. The team will adopt the conventions
that are relevant to the project instead of following every specific 
recommendation


For Python code, the team will follow
\href{https://peps.python.org/pep-0008/}{PEP 8 -- Style Guide for Python Code}.
which includes conventions for indentation, naming, whitespace, imports, and the general code layout.


Coding standards will be enforced through automated formatting and the use of linting checks where applicable.
These checks will be included in the project's CI workflow and must pass. Pull request reviewers will also verify that code
follows the team's coding standards before approving a merge.

\section*{Appendix --- Team Charter}


This appendix sets out the expectations that team members have agreed to hold each other to throughout the project.

\subsection*{External Goals}

The team's external goals are to use FitFolio as an opportunity to showcase the 
technical skills developed throughout the entirety of the Software Engineering program 
while producing a project that can be presented outside of the course.

The team aims to:

\begin{itemize}
  \item Produce a high-quality project that performs well against the evaluation criteria
  \item Develop a polished, usable high-quality application that is able to be demonstrated at the Capstone EXPO.
  \item Gain experience developing large software systems over multiple iterative development phases.
  \item Strengthen experience with software architecture, testing, code review, requirements, and project management.
  \item Create a project that team members can discuss during future technical interviews and include in portfolios.
  \item Gain experience working with and integrating real-world external services and managing the limitations that come with those services.
\end{itemize}

\subsection*{Attendance}
\phantomsection\label{sec:attendance}

\subsubsection*{Expectations}

It is expected that team members attend scheduled meetings, arrive on time, and be prepared to discuss
work assigned to them. Members should make an effort to attend all meetings with the project supervisor.

If a member expects that they will arrive late, leave early, or miss a meeting, they must notify the team
as early as possible through Microsoft Teams. 
Any member who misses a meeting is responsible for reviewing the meeting notes and following up on any 
decisions, assigned tasks, or deadlines that affect their work.

Repeated attendence issues will be handled according to the thresholds defined in Table~\ref{tab:triggers}. Attendance falling below
the team's defined 80 percent threshold or two consecutive unexcused absences will trigger the 
corresponding team response.

\subsubsection*{Acceptable Excuse}

Acceptable reasons for missing a meeting or deadline include illness, family or personal emergencies,
major academic conflicts, interviews or employment obligations, and other
unexpected circumstances that prevent a member from attending or completing
work.

For expected/forseeable conflicts, team members should provide notice prior whenever possible.
Repeated unexplained absences, or failure to complete assigned work without communicating with
the team will be considered unacceptable.

\subsubsection*{In Case of Emergency}

If a team member experiences an emergency that prevents them from attending a meeting
or completing assigned work, they should inform the team as soon as it is reasonably possible
to do so.

The team can then determine if the affected work should be reassigned, delayed, or adjusted
based on the urgency of the task and the upcoming deadline. Once the team member is able to return
they are responsible for reviewing desicions made during their absence and coordinating with the team 
about any remaining responsibilities.

\subsection*{Accountability and Teamwork}

This subsection sets out what team members can expect from each other in terms of the quality of their work, their attitude, and staying on track.

\subsubsection*{Quality}
\phantomsection\label{sec:quality}

This subsection describes the standard of preparation and work expected from every team member.

\textbf{Meeting Preparation and In-Progress}
\begin{itemize}
    \item The meeting chair posts the agenda as a GitHub issue using an appropriate template (dependent on the meeting) at least 24 hours before the meeting. The meeting date must be visible within the issue title. Team members add their items/questions before it starts.
    \item Everyone arrives with a short update (done since last time, what's next, any blockers) and has their GitHub Projects cards up to date.
    \item Anything linked in the agenda, like a pull request or a draft section, is read before the meeting.
    \item All items discussed with their resulting outcome are documented in the GitHub issue, once the meeting is complete, it shall be marked as done.
\end{itemize}

\textbf{Quality Assurance} \newline
The following steps ensure each deliverable meets the course checklist and rubric before it is submitted:
\begin{itemize}
    \item Before starting any deliverable, every team member responsible for the feature must read through the checklist and rubric. Any questions and/or doubts must be raised as soon as possible.
    \item Each deliverable is assigned a QA reviewer, who must not be the main author. This role rotates between team members for each deliverable.
    \item At least 24h before the submission, the QA reviewer will go through the checklist and rubric to ensure all items are at least being met.
    \item Should an issue with the checklist and/or rubric arise, they must communicate through the GitHub issues and/or Teams channel for extra help from other team members.
    \item Team members may also request periodic check-ins with another team member who mutually agrees.
\end{itemize}

\textbf{Definition of Done} \newline
Every feature that is considered to have reached a certain goal/milestone needs the following within a pull request:
\begin{itemize}
    \item Linked to a specific GitHub issue.
    \item Passes all CI tests and formatting checks.
    \item (Unless otherwise stated) Tests for the new features with brief justification on why they exist and that they pass.
    \item Approved by at least one other team member who isn't the main author. In the case where all team members worked on a feature, everyone must approve it.
\end{itemize}

\subsubsection*{Team Building}

% \wss{How will you build team cohesion (fun time, group rituals, etc.)? } \\
The team will build cohesion through regular, low-effort rituals rather than occasional large events, since consistent contact matters more than one-off activities.

\begin{itemize}
  \item \textbf{Weekly check-in:} The first five minutes of every weekly team meeting are reserved for an informal check-in, where each member shares how they are doing, both within the project and outside it. 
  This helps the team notice early when a member is overloaded, and adjust workloads before deadlines are affected.
  \item \textbf{Deliverable retrospectives:} After each deliverable is submitted, the team holds a 20-minute retrospective during the next weekly meeting. 
  Each member shares one thing that went well and one thing to improve, and the team agrees on at least one change to try for the next deliverable. 
  This gives every member an equal voice, keeps small frustrations from building up, and feeds directly into each deliverable's reflection.
  \item \textbf{Using our own product:} Once the proof of concept is working, the team will hold a weekly step challenge using FitFolio itself. 
  This builds friendly competition within the team, and gives every member real experience as a user of the product, which will help identify usability issues early.
\end{itemize}

\subsubsection*{Decision Making}
\phantomsection\label{sec:decision-making}

% \wss{How will you make decisions in your group? Consensus?  Vote? How will you
% handle disagreements? }

The team will aim to make decisions by consensus, since decisions that every member agrees with are more likely to be followed through. Decisions are made during the weekly team meeting, or in the group chat for decisions that cannot wait.

\begin{itemize}
  \item \textbf{Voting:} If consensus is not reached after 15 minutes of discussion, the decision is made by majority vote. 
  A vote requires at least four of the five members to be present or to respond in the group chat, and passes with at least three votes in favour, so that no decision is made by a minority of the team.
  \item \textbf{Area decisions:} Technical decisions within a specific area of the app (e.g., the health data integration or the market engine) are made by the members working on that area, who inform the rest of the team. 
  Any member may ask for such a decision to be brought to a team vote.
  \item \textbf{Scope decisions:} Decisions that change the product's scope or vision, such as removing a feature, are brought to the supervisor before being adopted.
  \item \textbf{Recording decisions:} Every decision and its reasoning is recorded in the relevant meeting issue, so that settled decisions are not revisited without new information.
\end{itemize}

When disagreements arise, each side will explain their position with a focus on what is best for the project rather than personal preference. 
If the same disagreement remains unresolved after two consecutive team meetings, it will be raised with the supervisor, who will help the team reach a decision.
