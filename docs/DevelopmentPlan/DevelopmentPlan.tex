\section{Team Member Roles}

The team will use adapting roles over the course of the project. 
Instead of assigning each member to one responsibility for the entire project timeline, 
roles can change between meetings, development phases, and deliverables
depending on the needs of the team and the members.

The anticipated team roles include: 

\begin{itemize} 
    \item \textbf{Meeting Chair:} Leads team meetings to ensure that the agenda is followed
    as well as keeping discussions focused to ensure action items are assigned

    \item \textbf{Notetaker:} Records important decisions, deadlines, and questions asked during meetings
    as well as information discussed during lectures

    \item \textbf{Project Coordinator:} Monitors GitHub issues, milestones and the GitHub project board to ensure the work
    remains aligned with the upcoming dealines.

    \item \textbf{Developer:} Implements assigned features, resolves technical issues, contributes
    to relevant implementation documentation.

    \item \textbf{Reviewer:} Reviews pull requests submitted by other team members and ensures any documentation
    or code is consistent with the team's coding standard.

    \item \textbf{Testing and Quality Assurance:} Develops and executes tests, identifies defects, and verifies
    that implemented functionality satisfies the corresponding requirements.
\end{itemize}

All team members will contribute to development, testing, documentation, and code review
throughout the project and the aforementioned roles will rotate between members so that
responsibility is shared across the team.

\subsection{GitHub Projects}

The team will use a GitHub Project board to track all issues. The board will have the columns \textit{Backlog}, \textit{In Progress}, \textit{In Review}, and \textit{Done}. Issues move to \textit{In Review} when a pull request is opened, and to \textit{Done} automatically when the linked issue is closed by a merged pull request. The board can be filtered by milestone, assignee, or label, giving the team and supervisor a clear view of who is working on what and what remains before each deadline.

The GitHub Project can be found here: \href{https://github.com/users/davislenover/projects/4/views/1}{FitFolio GitHub Project}.

\section{Coding Standard}

The development team will adopt a similar standard to the Microsoft TypeScript Coding Guidelines
as the primary guideline for any code written throughout the project.

The team will follow applicable conventions from this guideline, including:


\begin{itemize}
    \item Using PascalCase for type names and enum values
    \item Using camelCase for functions, properties, and local variables
    \item Avoiding the use of the I prefix for interface names
    \item Separating logical components into appropriate files
    \item Exporting types and functions only when they are required by other modules
    \item Placing type definitions before their use where practical
    \item Preferring undefined over null
    \item Using double quotation marks for strings.
    \item Using four spaces for indentation
\end{itemize}

Some standards in the Microsoft TypeScript Coding Guidelines do not 
apply directly to BurnNEarn, the team will adopt the conventions
that are relevant to the project instead of following every specific 
recommendation

\subsection*{External Goals}

The team's external goals are to use BurnNEarn as an opportunity to showcase the 
technical skills developed throughout the entirety of the Software Engineering program 
while producing a project that can be presented outside of the course.

The team aims to:

\begin{itemize}
  \item Product a high quality project that performs well against the evaluation criteria
  \item Develop a polished, usable high quality application that is able to be demonstrated at the Capstone EXPO.
  \item Gain experience developing large software systems over multiple iterative development phases.
  \item Strengthen experience with software architecture, testing, code review, requirements, and project management.
  \item Create a project that team members can discuss during future technical interviews and include in portfolios.
  \item Gain experience working with and integrating real world external services and managing the limitations that come with those services.
\end{itemize}

\subsection*{Attendance}

\subsubsection*{Expectations}

It is expected that team members attend scheduled meetings, arrive on time, and be prepared to discuss
work assigned to them. Members should make an effort to attend all meetings with the project supervisor.

If a member expects that they will arrive late, leave early, or miss a meeting, they must notify the team
as early as reasonably possible through the team's primary communication channel. 
Any member that misses a meeting is responsible for reviewing the meeting notes and following up on any 
decisions, assigned tasks, or deadlines that affect their work.

\subsubsection*{Acceptable Excuse}

Acceptable reasons for missing a meeting or deadline include illness, family or personal emergencies,
major academic conflicts, interviews or employment obligations, and other
abnormal circumstances that reasonably prevent a member from attending or completing
work.

For foreseeable conflicts, team members should provide notice prior whenever possible.
Repeated unexplained absences, or failure to complete assigned work without communicating with
the team will be considered unacceptable.
